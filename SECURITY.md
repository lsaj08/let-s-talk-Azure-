# Security boundary and observed evidence

## Local Codex / Claude Code boundary

The local stdio server trusts its operator-controlled startup arguments and installed Azure CLI executable. MCP tool arguments, template JSON, CLI JSON output, and Azure resource names are untrusted data. The model cannot select a subscription/group/type allowlist, executable, URL, or CLI command through a tool. Process startup binds the project scope. Each operation constructs a fixed CLI argument array; only inspection, validation, what-if, and existing deployment status are exposed. There is no local mutation, shell, token, login, or RBAC tool. This restriction is enforced by the tool dispatcher, not by MCP annotation hints.

Validation and what-if send templates to Azure. They reuse the hosted template policy, including checks on parameter default values. Inputs are non-confidential JSON only, stored briefly in random temporary directories and removed in finally. POSIX file permissions are restricted; Windows inherits the current user's temporary-directory ACL. An unexpected process crash may leave temporary files. Do not supply confidential literals: field-name checks cannot identify every secret. Inventory outputs use explicit projections and a second field filter; what-if omits property values. Raw CLI stdout on failure and stderr are never returned. Stdout is reserved for bounded MCP JSON-RPC messages; execution has output and time limits.

Azure CLI owns the credential cache, including refresh tokens. This project does not retrieve or persist tokens. Cache encryption depends on the platform; do not copy `.azure` into a project or repository. An operator, compromised CLI, process running as the same user, or a parent agent with independent shell access can bypass local tool restrictions. Optional subagents reduce shell access; prompt instructions are not a security sandbox. Do not grant the parent broader Azure permissions simply because the server has restricted tools.

Local checks use simulated Azure JSON, real controlled child processes, and stdio handshake tests. Windows az.cmd arguments are quoted and expansion/operators are rejected; executable discovery trusts the operator's PATH. Timeouts attempt to terminate processes, but Windows batch process-tree termination is best effort and does not prove an Azure operation was canceled. Actual CLI sign-in, Azure provider/RBAC behavior, Unix runner behavior, and full Codex/Claude integration remain live acceptance gates. The local preview is resource-ID-only and predictive; it is not authorization to deploy. Changes require a distinct reviewed approval workflow outside this local tool surface.

## Hosted boundary

Sources considered attacker controlled: MCP arguments, ARM templates and parameters, OAuth query parameters, review IDs, browser forms and Azure polling URLs. ARM resource state and tool output are data, never instructions to grant access or approve changes.

Flow: Sites authenticated identity -> per-user encrypted R2 record -> validated tenant/subscription configuration and per-user approved project group/types -> ARM request on fixed management.azure.com -> encrypted plan -> same-user private browser review -> origin/fetch-metadata and random nonce check -> digest and scope verification -> conditional R2 compare-and-swap -> single PUT to the saved deployment URI.

Sensitive sink: ARM PUT deploys the immutable saved template. The MCP surface exposes no approval or deployment tool. User-supplied subscription, tenant, URL and mode arguments cannot redirect this sink; server configuration controls tenant/subscription; an immutable human-approved project record controls resource-group scope and types. Policy rejects cross-scope/nested expressions, linked templates, IAM and scripts before Azure calls. R2 conditional put consumes approval before calling Azure, including concurrent submissions. A failed/uncertain PUT remains consumed, requiring deployment inspection before another plan.

Authentication: Sites platform identity is distinct from Azure consent. OAuth state is random, user-bound, encrypted, expires, and is consumed atomically before code exchange. PKCE binds the authorization code to a server-held verifier. Tokens come only from the fixed tenant Microsoft token endpoint, never from MCP input. The subscription tenant is checked through ARM before saving a connection. Credentials are runtime secrets, never package values; tokens are AES-GCM encrypted with object key as associated data. No refresh token requested.

Fail closed: missing config/storage/key, expired token, missing identity, another user's plan, invalid OAuth state, replay, changed scope/digest, expired plan, unknown/delete/ignore what-if changes, diagnostic error, invalid URL or concurrency conflict. Azure response body is not included in failure messages. Sensitive property names and sensitive delta paths are redacted in successful outputs; redaction is best effort and users must not supply any confidential template values.

Verified locally: policy, authorization, state expiry, SSRF host boundary, encryption context, atomic consumption, exact saved payload and replay prevention. Azure responses and R2 are simulated. A live Entra application was registered and the consent screen was reviewed, but the latest OAuth callback failed. Not verified: successful live token exchange and connection, actual Azure RBAC, Azure API long-running response variants, Cloudflare R2 conditional writes in production, browser navigation/header behavior, real Azure deploy success, platform filtering of identity headers. These are integration acceptance gates before operational use.

Residual boundaries: this code trusts the Sites gateway, runtime secret administration, Azure and storage; a privileged operator can change configuration/source. Browser approval is a user UX boundary, not a hardware-backed human-presence proof. Azure drift between what-if and deployment remains possible. Input size limits do not establish full per-user rate limits. Retention cleanup and external audit sink are not implemented. Plan state retains the approval actor and timestamp; Azure Activity Log provides actual Azure actions.

Project contract: encrypted projects/<id> records are owned by the Sites user and bound to tenant/subscription, exact group, literal resource-type allowlist, trusted creation body and digest. Each prepare_project produces a new immutable proposal; no caller can replace an existing project or pass a raw subscription template. Existing group selection changes only private authorization. New group creation uses a server-built subscription deployment with exactly one Microsoft.Resources/resourceGroups resource. What-if must show precisely Create on the exact group ID. Approval rechecks absence, atomically consumes the proposal, and submits once. project_status activates the project only after Succeeded and an ARM group read; failures/unknown status leave resource deployments blocked. Changing scope/types requires a new proposal. Group-name races after approval cannot be frozen atomically by ARM; what-if remains predictive.

Project tests add: sign-in without a fixed group; preapproval deployment denial; another-user access denial; no Azure writes for existing-group selection; concurrent new-group approval sends exactly one trusted group deployment; activation waits for Succeeded; wildcards/privileged types rejected; existing groups cannot silently be targeted by a create proposal. All Azure behavior is simulated locally.
